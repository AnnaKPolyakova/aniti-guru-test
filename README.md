# Pay_system (aniti-guru-test)

Платёжная система для заказов: оплата через эквайринг, возвраты наличными, учёт статусов заказов и платежей.

## Стек технологий

- **API**: FastAPI, Uvicorn
- **БД**: PostgreSQL 16, SQLAlchemy 2, Alembic, asyncpg / psycopg2
- **Очереди и кэш**: Redis, Celery
- **Авторизация**: FastAPI-Users, JWT (access + refresh в cookie)
- **Конфигурация**: Pydantic Settings, dotenv
- **Логирование**: Loguru
- **Тесты**: pytest, pytest-asyncio, pytest-cov, httpx, Faker, factory_boy
- **Качество кода**: Ruff, isort, Flake8, Mypy, pre-commit

## Назначение проекта

Система позволяет:

- **Регистрироваться и авторизовываться** по JWT (access-токен в теле ответа, refresh — в cookie).
- **Создавать платёж пополнения по заказу через эквайринг** — инициация оплаты во внешнем банковском API, сохранение платежа с `bank_payment_id`, постановка в очередь задачи на проверку статуса.
- **Создавать возврат по заказу** — наличными, в пределах уже оплаченной суммы; статус оплаты заказа пересчитывается сразу.
- **Фоново проверять статус эквайринговых платежей** — воркер Celery опрашивает API банка и обновляет статус платежа и заказа; раз в 3 часа запускается задача, которая ставит в очередь проверку всех незавершённых платежей.

## Основные сущности и логика

### Пользователи и авторизация

- **Пользователь** — email, пароль (хеш), имя, телефон; флаги активность/суперпользователь/верификация (FastAPI-Users).
- **JWT**: access-токен (короткий TTL) и refresh-токен (дольше), refresh передаётся в cookie.
- **Выход**: refresh-токен добавляется в чёрный список в БД (`revoked_tokens`), cookie очищается. При проверке access-токена чёрный список учитывается.

### Заказы

- **Заказ** принадлежит пользователю, имеет `total_sum` и **статус оплаты**:
  - `unpaid` — не оплачен;
  - `partially paid` — оплачен частично;
  - `paid` — оплачен полностью.
- Статус заказа вычисляется по **завершённым** платежам: сумма депозитов минус сумма возвратов сравнивается с `total_sum`.

### Платежи

- **Платёж** привязан к пользователю и заказу.
- **Тип операции**: `deposit` (пополнение) или `return` (возврат).
- **Тип платёжного средства**: `cash` (наличные) или `acquiring` (эквайринг).
- **Статус платежа**: `submitted`, `processing`, `completed`, `rejected`.
- У эквайринговых платежей хранится `bank_payment_id`; у завершённых может быть `paid_at`.

**Пополнение через эквайринг:**

1. Пользователь вызывает `POST /payments/deposit/acquiring` (order_id, amount).
2. Проверяется существование заказа, принадлежность пользователю и что сумма не превышает остаток к оплате (учёт уже созданных, но ещё не отклонённых платежей).
3. Вызов внешнего API эквайринга «старт платежа» → получение `bank_payment_id`.
4. В БД создаётся платёж со статусом `submitted`, ставится в очередь Celery-задача проверки статуса.
5. Воркер периодически (сразу после создания и при повторных попытках / по расписанию) вызывает API «проверка платежа», обновляет статус платежа и при переходе в `completed`/`rejected` пересчитывает `payment_status` заказа.

**Возврат:**

1. Пользователь вызывает `POST /payments/return` (order_id, amount).
2. Проверяется заказ, принадлежность пользователю и что сумма возврата не превышает **уже оплаченный баланс** (только по завершённым платежам).
3. Созётся платёж типа return, cash, со статусом `completed`, сразу пересчитывается статус оплаты заказа.

## Запуск

Перед запуском приложения необходимо поднять базу данных в Docker:

```bash
docker compose -f docker-compose-local.yml up -d
```

После этого:

- **API**: `python -m src.app` или `uvicorn src.app.__main__:app --host 127.0.0.1 --port 8000`.
- **Документация API** (после запуска API): [Swagger UI](http://127.0.0.1:8000/docs), [ReDoc](http://127.0.0.1:8000/redoc).
- **Celery worker**: `celery -A src.app.celery worker -l info`.
- **Celery beat** (для периодической проверки платежей каждые 3 часа): `celery -A src.app.celery beat -l info`.
- **Миграции**: `alembic upgrade head`.

Конфигурация через переменные окружения (см. `.env` и `src/app/core/config.py`): PostgreSQL, Redis, JWT, URL эквайринга и др.
